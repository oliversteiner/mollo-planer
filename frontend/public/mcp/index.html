01 IDENTITY & ACCESS

Your access starts with the team.

People connect their personal account using the credential shown once in their profile. Agents instead use a dedicated agent account, not a team member’s account: ask the Planer administrator to create it, add it to the required projects with the Agent role, and provide an MCP credential. Agent accounts are provisioned by an administrator and cannot sign in to the web interface.

↗

Your token is a secret. It is shown only once. Store it in your agent’s secret manager or protected local configuration—never in prompts, repositories, logs, or screenshots.

The server checks every request as the account. You can only see approved projects and perform actions for which that account has permission. Personal credentials expire after 90 days; the administrator can revoke or renew agent credentials.

02 CONNECTION

Connect your agent to the MCP server.

Add the endpoint and token to your client’s MCP configuration. The .dev host is TEST and .ch is PRODUCTION; for local work, use the API address confirmed by your team. Send the token as Authorization: Bearer ….

Claude Desktop

Configure the remote server with mcp-remote. The local configuration contains the token and must be protected; never commit it to version control. Node.js must be available on the computer.

{
  "mcpServers": {
    "mollo-planer": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://api.planer.example.com/mcp", "--header", "Authorization:${AUTH_TOKEN}"],
      "env": { "AUTH_TOKEN": "Bearer <your-agent-token>" }
    }
  }
}

Replace the placeholder locally, protect the configuration file, and never share it with the real token. Fully quit and restart Claude Desktop to load the configuration.

Claude Code

Put the server in the .mcp.json of the project. The file may be committed because it holds only the name of an environment variable, never the token. Use one variable per account: MOLLOPLANER_<NAME>_TOKEN, for example MOLLOPLANER_BOB_TOKEN for the agent Bob.

{
  "mcpServers": {
    "mollo-planer": {
      "type": "http",
      "url": "https://api.planer.example.com/mcp",
      "headers": { "Authorization": "Bearer ${MOLLOPLANER_<NAME>_TOKEN}" }
    }
  }
}

Claude Code reads ${…} in url and headers when it starts, so the token stays in your environment (not in a file under version control). Set the variable and start Claude Code again; check with claude mcp list. Do not name the variable like a credential of another tool (ANTHROPIC_API_KEY, NPM_TOKEN …): Claude Code reads those as empty in headers. With an Authorization header set, Claude Code does not fall back to OAuth for this server. Alternatively, on the command line: claude mcp add --transport http mollo-planer https://api.planer.example.com/mcp --header 'Authorization: Bearer ${MOLLOPLANER_<NAME>_TOKEN}' (keep the single quotes).

Custom Connector with OAuth (people)

People can connect Claude (Desktop or claude.ai) without a token and without Node.js: Settings → Connectors → add a Custom Connector with the address https://api.planer.example.com/mcp. Claude finds the sign-in itself, you approve it once, and Claude then works with your rights. This is for the accounts of people. An agent account cannot sign in on the web and uses the token as described above.

JetBrains AI Assistant

Open Settings → Tools → AI Assistant → Model Context Protocol (MCP), choose Add → As JSON and paste this configuration. Like Claude Desktop, it uses mcp-remote; replace the placeholder locally with your token. On Windows, npx starts through cmd /c.

{
  "mcpServers": {
    "mollo-planer": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://api.planer.example.com/mcp", "--header", "Authorization:${AUTH_TOKEN}"],
      "env": { "AUTH_TOKEN": "Bearer <your-agent-token>" }
    }
  }
}

Menu paths can differ between IDE versions. Apply the configuration and restart the IDE afterwards. The token does not belong in project files that are under version control.

JetBrains Junie

Add the server via Settings → Tools → Junie → MCP Settings, or edit the user file ~/.junie/mcp/mcp.json directly. Remote servers are described with url and headers. The token belongs only in the user file ~/.junie/mcp/mcp.json, never in the project-wide .junie/mcp/mcp.json, which can be versioned.

{
  "mcpServers": {
    "mollo-planer": {
      "url": "https://api.planer.example.com/mcp",
      "headers": { "Authorization": "Bearer <your-agent-token>" }
    }
  }
}

Menu paths can differ between IDE versions. Apply the configuration and restart Junie or the IDE afterwards.

03 CAPABILITIES

Choose the right tool.

When connected, the server provides its instructions and thirteen tools. Start with list_projects to check project IDs, roles, and revisions; add include_rights: true or include_members: true when needed. Read only the information needed for the task.

list_projectsProjects you can see and their permissions
list_templatesAvailable project templates
list_usersPeople, subject to your permissions
export_planRead a plan: whole, filtered or as an outline
list_tasksFind tasks, flat and short; one task with detail
get_project_statisticsThe numbers of a project without reading the plan
import_planApply plan changes after permission checks
update_tasksUpdate status, commit, or assignment
add_comment list_commentsWrite and read comments
create_idea list_ideasCreate and view private ideas
get_project_ai_contextRead project knowledge shared for AI tools

A plan uses the planer-v2 format and the hierarchy Project → Milestone → ToDo → Task. Keep existing IDs such as m-42, t-81, and k-105; use IDs such as m-new-1 for new items. The server assigns their permanent IDs. Lists return has_more and next_cursor; follow the cursor until there are no more results. Retrieve truncated comments and ideas by their ID and the next text offset.

Work cheaply

A whole export of a big project costs about 20,000 tokens, and most of its tasks are usually done. Read in stages:

  1. 1

    Overview. list_projects (IDs, revision), then get_project_statistics or export_plan with view: "outline" (about 1,000 tokens).

  2. 2

    Find work. list_tasks with assignee: "me" and status: ["open", "in_progress"]. One task with everything: list_tasks with ids and include: ["description", "comments"].

  3. 3

    Report progress. update_tasks directly: no export, no dry run first. base_revision is optional.

  4. 4

    Change structure. export_plan for one milestone, edit it, import_plan with mode: "partial". The whole export only to rebuild the whole plan.

The same recipes in plain Markdown: /mcp/llms.txt.

04 SAFE WRITES

Review first. Then apply.

  1. 1

    Export selectively. For large plans, filter by version, milestone, task status, or unreleased milestones.

  2. 2

    Preserve IDs and revision. Keep exported IDs and use the current revision for full-plan changes. For update_tasks, base_revision is optional: without it every task and field is changed on its own; with it the call is refused if the plan changed since, and the answer carries the current state of your tasks.

  3. 3

    Run a dry run first for import_plan. Call it with dry_run: true and review all changes and errors before a real write; a dry run does not reserve a revision. update_tasks is atomic and checked: no dry run needed (dry_run: true stays possible).

  4. 4

    Choose the right mode. A filtered export is an excerpt: write it back only with mode: "partial". full treats the input as the entire plan and moves missing items to the recycle bin. In partial an existing item needs only its id and the fields that change; what is missing stays unchanged, revision and project may be left out, labels and assignees are taken from the project. base_revision stops the import if the plan is newer.

!

Never set milestone or ToDo status directly: those statuses are derived from tasks. Only set task statuses such as idea, planned, open, in_progress, review, or done.

update_tasks changes only supplied fields; commit: null and assigneeEmail: null clear those values. partial adds or updates but never deletes. A title (milestone, ToDo, task) has 2 to 160 characters; a longer one is refused. Unknown fields in a document are refused too, with the path and a suggestion; the form is described by the JSON schema (also linked in the instructions the server sends). A dry run does not replace permission checks: the server validates every field and action again. Notifications to assignees are off by default; enable them only when the task requests it.

05 TROUBLESHOOTING

If the connection gets stuck.

401 · Unauthenticated
Check the token. It may be invalid, revoked, or expired; ask the administrator for a new credential.
403 · Not authorised
The account may lack MCP access or the required project permission. Ask the team to check membership and permissions.
429 · Too many requests
Wait briefly before trying again. The server limits request rates.
Server not listed
Check the MCP configuration and fully restart your client.
